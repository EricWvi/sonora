- **导入在线专辑**（Eric 确认方案，2026-11-06；阶段 7 的后续工作，SPlayer 没有这个功能）：入口是在线专辑页的“更多 → 导入专辑到曲库”（在线专辑页原来没有“更多”，现在只有可以导入的用户才有）与在线专辑卡片的右键菜单；组外成员没有入口，服务端同样返回 403。决定如下：
  - **专辑艺术家用网易云的**，每首歌的艺术家仍是它自己的。这是单曲导入规则（专辑艺术家等于歌曲艺术家）的例外：真实抽样的 25 张专辑中有 5 张歌手不一致，一张 32 首有 18 种组合，按单曲规则会拆成 18 张。合辑的专辑艺术家会是“群星”这类名字。
  - **专辑键**：新专辑的 `artist_key` 带 `#netease:album:<专辑 ID>` 后缀，与单曲导入的 `#netease:<歌曲 ID>` 一样能与同名专辑并存，编辑与合并沿用现有处理；网易云上只有 1 首时才标“单曲”；网易云的简介在专辑简介为空时写入。
  - **已导入过的歌**：还独占单曲导入建的专辑的，移入整张专辑并补音轨号与碟号（只改数据库，文件标签不动），空出的专辑删除；已在管理后台合并到别处的不动，只算“已在曲库”。
  - **并入哪张专辑**：优先关联了这张网易云专辑、且不是单曲导入建的专辑（再次导入、管理后台填过网易云 ID 的专辑，或合并过这张专辑的单曲而带上网易云 ID 的专辑），只导缺的歌；否则新建。注意：把导入的单曲合并进上传的专辑后，那张上传专辑会带上网易云专辑 ID，之后导入整张时其余的歌会并入它；上传过的歌按“已上传的同名专辑”的规则不匹配，会再导入一份，同一张专辑里出现重复的歌。
  - **已上传的同名专辑**：并存，不按歌名自动匹配，确认框提示同名专辑的数量，由管理后台合并。导入的文件写了标签，哈希不会与上传的相同，所以同一首歌可能有两份。
  - **音轨号与碟号**写入 ID3（`TRCK`、`TPOS`）与数据库，专辑页的碟号分组与曲目序号直接生效。网易云的碟号有 `"01"`、`"1"`、`"02 [Target Deluxe Edition]"` 等写法，只取开头的数字；`/album` 的歌曲没有发行时间，年份取专辑的。
  - **进度与并发**：服务端后台任务，所有用户一次一张、逐首下载，单曲导入可以插在两首之间；任务只在内存中，服务重启后丢失，已入库的歌保留，再导入一次即可补齐。确认框先显示“将导入、已在曲库（其中移入）、无法播放”的数量；进度用现有的 `$message` 加载提示（`正在导入《专辑》 3/32`），结果用提示或现有对话框，不新增视觉样式；刷新页面后接着显示未完成的导入。
  - **部分失败**：不可播放、没有完整版本、不是 MP3、下载失败的歌跳过并列出原因；登录失效、退出网易云、网易云限制请求频率或接口服务不可用时中止，已导入的保留。
  - **请求间隔与限流**（Eric，2026-11-07）：专辑导入向网易云取歌（播放地址、歌词与文件）的间隔至少 5 秒，从上一次取歌算起，所以已在曲库、移入或不可播放的歌最多在一次取歌之后等一次；等待在导入锁之外，单曲导入不受影响；确认框写明“每首歌间隔 5 秒”。真实导入 8 张、73 首时没有间隔，也没有遇到限流，这个间隔是预防，没有证据说明它必要。网易云返回 405（操作频繁）或 -460（Cheating）时，接口服务把 405 作为 HTTP 状态、-460 作为 400 照原样转来（核对了镜像 4.41.1 的 `util/request.js`），原来 Sonora 把它们当成普通结果，取播放地址时会误报为“账号没有完整版本”并继续下一首；现在识别为限流：专辑导入中止并提示“网易云请求过于频繁，请稍后再导入”，其他接口返回 429 `netease_throttled`。这两个错误码来自对网易云接口的了解，没有真实触发过。证据：Go 测试 `TestThrottledCodes`、`TestNeteaseAlbumImportStopsWhenThrottled`（限流后不再请求后面的歌）、`TestAlbumImportWaitsBetweenSongs`（两次下载之间至少两个间隔，总时长不超过 3.5 个间隔）、`TestNeteaseImportRefusals`（单曲 429）；其他测试把间隔设为 0，不等待。

## 已知缺陷与支持限制（1.0.0）

支持范围：

- 只支持桌面版 Chrome，不考虑移动端与其他浏览器；最小窗口宽度 990px。镜像只构建 `linux/amd64`。
- 音乐只能经管理后台上传，不支持把文件直接放进存储卷；不做转码，只支持 MP3、FLAC、AAC（M4A）、Ogg Vorbis、Opus。
- 与网易云接口相关的页面和入口都没有做；不提供托盘、全局快捷键与桌面窗口行为。
- 不做自动备份，升级前由 Eric 手动备份数据卷，见[部署说明](../deployment.md#升级与恢复)。

已知缺陷与限制：

- 播放中电脑睡眠会暂停播放，唤醒后不自动续播，要手动播放（媒体键或页面按钮）。
- 断网或服务不可达时，播放端没有重试逻辑：当前歌曲靠缓冲继续，“下一首”连续三首失败后暂停，恢复后要手动播放。
- 与 SPlayer 相同、未改动的 Media Session 行为：跳转到 0 秒的请求被忽略；封面的 `type` 一律写 `image/jpeg`。
- 上传时歌词只按文件名（不含目录）与音频配对：一次拖入的多个文件夹中如果有同名文件（例如都有 `01.flac`、`01.lrc`），歌词可能配给别的文件夹的歌曲，多出的歌词显示的失败原因也不对。拖放文件夹时不在 `accept` 内的文件（封面图、`.cue` 等）被直接忽略，列表中不显示。
- 去重只按文件内容：同一录音的不同编码会各自入库；不检测音频帧级损坏。
- 搜索只有子串匹配，没有拼音、首字母、繁简与模糊搜索（阶段 8 候选）；歌曲搜索扫全表，1 万首时 40–55 ms。
- 管理后台的登录与初始化按用途全局限流，不区分来源：他人持续尝试时管理员也要等限流窗口结束。
- 播放器样式切换与展开动画的过程没有与 SPlayer 对照（视觉欠账，首版不补采）。
- 阶段 5 搁置：搜索框右键菜单、专辑与艺术家卡片的右键菜单、详情页批量操作。
