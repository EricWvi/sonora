# Sonora 重写路线图

更新日期：2026-10-24。状态：已完成独立工程与前端展示初始化，阶段 1（Go 服务基础与管理后台）已实现，其余阶段按验收条件推进。

## 1. 目标与已确定的约束

Sonora 重新实现播放器的业务和数据架构，界面样式完全按照 `reference/SPlayer` 还原。重写的原因是原项目与网易云音乐耦合过深，后续修改成本高。这个方向已由 Eric 确定，见[项目说明](../README.md)。

**复刻 SPlayer 的视觉是已确定的硬性约束，不属于下文可选的实施建议。** 2026-10-24 Eric 明确了范围：

- **播放器严格复刻**：全屏播放器（及其各种模式与背景）、底部播放栏、播放队列抽屉的布局、配色、字体、字号、间距、尺寸、图标、圆角、阴影、透明度、动效和交互状态，以 `reference/SPlayer` 的源码与实际渲染为准逐项还原，并以截图对照验收。
- **SPlayer 所有视觉相关代码都复刻**：全局主题、封面动态取色、Naive UI 主题覆盖、全局与组件样式、动效，以及歌词样式和播放器外观等设置项。
- **其他页面视觉语言一致**：使用同一套颜色、字体、圆角、阴影和组件，页面结构与信息组织按 Sonora 的流媒体体验自行设计，见[阶段 2 已确定的页面清单](phase/phase-2-player-baseline.md#已确定2026-10-24)。

未经 Eric 明确同意，不得改动上述视觉方案；新增的视觉元素（如专辑详情的碟号分组）沿用 SPlayer 的视觉语言并经 Eric 确认。功能完成不能代替第 6 节的视觉验收。

音乐服务方向已确定：Sonora 舍弃网易云音乐来源，使用我们自己开发的音乐服务，不实现网易登录、Cookie 导入、网易接口适配或网易播放地址解析。原项目的网易相关源码只用于识别需要移除的耦合；原账号仅用于查看参考界面的不同状态。

Eric 已明确：Web 前端技术栈按照 SPlayer，明确舍弃 Electron，后端使用 Go，当前后端只建占位目录。

2026-10-23 Eric 确定首发范围：

- **只支持桌面版 Chrome，不考虑移动端。**
- **Sonora 是自托管的音乐流媒体服务。** “自研音乐服务”由三部分组成：播放端（Web，严格复刻 SPlayer 样式，体验是流媒体服务，不接触文件和目录，没有文件夹浏览）；另行开发的管理后台（Naive UI 默认风格，上传音乐并维护曲库）；Go 服务（运行在容器中，音乐文件存放在服务独占的挂载卷，为播放端和管理后台提供 API 与音频流）。
- **音乐只能通过管理后台上传入库**，不支持手动往挂载目录放文件。
- **认证：** 播放端通过 OIDC 登录 Authelia，代码完全照搬 `../homepage`，喜爱、歌单与历史按用户隔离；管理后台在首次使用服务时，于页面上输入容器日志中的一次性初始化 token、用户名和密码创建管理员，不走 OIDC。开发环境写死一个管理员和一个普通用户。
- **先做管理后台**；播放端页面清单等实际开始做播放端时再定。
- **首页**：问候语、快捷入口、最近添加的专辑与最近播放（2026-10-24 由“纯静态”调整）。
- **播放端只做流媒体服务的常见播放功能。** 与网易云接口相关的页面和入口全部不做，原项目的大部分在线页面因此不在范围内，页面清单草案见[阶段 2 计划](phase/phase-2-player-baseline.md)。
- **标志图形暂时复用；所有 SPlayer 名称与文字换成 Sonora。**
- **播放器的视觉基线直接截取本机参考实例，歌曲数据来自网易云。** 其他页面不设逐页基线，按第 6 节检查视觉语言是否一致。管理后台在 SPlayer 中没有对应界面，不受复刻约束，采用 Naive UI 默认风格。

Go 服务已在阶段 1 实现管理员初始化、上传入库与管理 API（2026-10-24）；为照搬 homepage 的 OIDC，沿用其 `net/http`、SQLite 与配置方式。阶段 4 已照搬 homepage 的 OIDC，并实现播放端的曲库、喜爱、歌单与历史 API（2026-10-24），见 [Sonora API 约定](api.md)；播放状态等其余契约尚未实现。阶段顺序是建议。

## 3. 重写要解决的具体问题

| 原项目现状与证据 | 对修改的影响 | Sonora 的目标 |
| --- | --- | --- |
| 请求默认走网易接口，并在请求参数中拼接 `MUSIC_U`，见 [request.ts](../reference/SPlayer/src/utils/request.ts) | 页面、鉴权与单一平台请求方式绑定 | 平台请求与会话只在对应 Adapter 内处理 |
| 用户区域主动检查网易登录并刷新用户资料，见 [User.vue](../reference/SPlayer/src/components/Layout/User.vue) | 无账号、账号过期与播放器初始化容易相互影响 | 登录状态属于具体来源，播放器可以独立启动 |
| 路由以 `needLogin` / `needApp` 判断访问权限，见 [router/index.ts](../reference/SPlayer/src/router/index.ts) | 平台身份与本地能力混为全局条件 | 依据页面真正需要的来源会话或运行环境能力判断 |
| `SongType` 混合数字 ID、会员标记、云盘、本地路径和流媒体服务器字段，见 [types/main.ts](../reference/SPlayer/src/types/main.ts) | 新来源要迎合既有字段，同 ID 也可能产生歧义 | 自有媒体身份与来源引用分离，平台字段不进入通用模型 |
| 播放控制器直接读写多个 Pinia Store，歌曲管理器分支处理来源，见 [PlayerController.ts](../reference/SPlayer/src/core/player/PlayerController.ts)、[SongManager.ts](../reference/SPlayer/src/core/player/SongManager.ts) | 播放状态、取地址、UI 与持久化难以单独验证 | 播放会话只有一个状态所有者，来源解析可替换 |
| 主题由 Naive UI 覆盖、动态配色、全局 SCSS 和组件内样式共同决定，见 [Provider.vue](../reference/SPlayer/src/components/Global/Provider.vue)、[main.scss](../reference/SPlayer/src/style/main.scss) | 单独复制 CSS 无法得到完整原样式 | 固定视觉基线，并整体理解主题生成链路 |

不采用“复制整个项目后逐步删网易代码”的主路径。可以逐项复用已确认的视觉资源与局部实现，但每项都要交代来源、依赖和验证方式，避免旧 Store、请求逻辑和平台字段被一并带入。

## 4. 技术方向与需要先验证的选择

### 4.1 已确定的技术栈

Eric 已明确：Web 前端技术栈按照 SPlayer，明确舍弃 Electron，后端使用 Go，当前只初始化前端展示和后端占位目录。前端已采用 Vue 3、TypeScript、Naive UI、Pinia、Vue Router、VueUse、SCSS、Vite，以及 pnpm；依赖声明以参考项目为依据，通过锁文件记录实际解析版本。网易接口包、原生音频和与当前展示无关的业务依赖不迁入。

重新组织业务逻辑，不直接移植原页面的全部脚本。Vue SFC 将模板、逻辑、样式放在同一文件，因此复用视觉部分时要显式检查脚本依赖，不能把复制 `.vue` 文件当成纯样式迁移。参见 [Vue SFC](https://vuejs.org/guide/scaling-up/sfc) 和 [TypeScript 支持](https://vuejs.org/guide/typescript/overview)。

### 4.2 运行环境与后端范围

Sonora 前端以 Web 应用运行。明确舍弃 Electron，不继承主进程、预加载、IPC、桌面窗口管理、托盘、原生模块或桌面安装包行为。浏览器能力与 Go 服务职责按实际需求设计，不能通过重新加入桌面宿主来满足原项目功能。

严格复刻的对象是 SPlayer 的 Web 界面样式。原生标题栏、系统托盘、桌面歌词和窗口行为不在继承范围内；不能把样式一致解释为需要复用桌面运行方式。

`backend/` 是 Go 实现的 Sonora 服务，负责接收管理后台上传的音频并入库、标签与封面读取、曲库索引、歌单/喜爱/历史等用户数据、歌词以及支持 Range 的音频流，并为管理后台提供独立的管理 API。文件路径只在服务内部使用，不出现在播放端 API 中。服务以容器运行，媒体存储卷与数据卷分别挂载；播放端使用照搬自 `../homepage` 的 OIDC 登录与会话；管理 API 使用管理员的独立会话。为原样复用该代码，Go 服务沿用 homepage 的标准库 `net/http`、modernc SQLite 与 YAML 配置。管理 API 与通用约定已在阶段 1 确定，见 [Sonora API 约定](api.md)。

## 5. 拟议模块与数据契约

模块应把复杂行为藏在小而稳定的 Interface 后面。Seam 放在实际会变化的位置：音频引擎、媒体来源、存储、运行环境。不先建插件市场、运行时插件系统或覆盖所有平台的巨大接口。

| Module | 对外承担的行为 | 内部处理的复杂性 |
| --- | --- | --- |
| Playback | 播放队列、播放/暂停、跳转、上一首/下一首和状态订阅 | 解析、加载、过期请求取消、错误分类、曲目切换与资源释放 |
| Library | 喜爱、歌单与播放历史 | 持久化、事务、排序与数据迁移 |
| Catalog | 浏览、搜索曲库中的歌曲、专辑、艺术家、歌单 | 分页、排序、缓存和 Go 服务 DTO 转换 |
| Service Connection | 与 Go 服务的连接、版本与当前登录用户 | 不可达与恢复；会话失效时跳转 `/auth/login` |
| Lyrics | 获取与解析歌词、按时间输出可渲染内容 | LRC/逐字格式、翻译、音译与偏移 |
| Web Platform | 媒体会话、页面内快捷键与 Chrome 能力检测 | 自动播放限制与权限；文件管理由 Go 服务承担 |
| Presentation | 按 SPlayer 样式展示 ViewModel 并发出用户意图 | 主题和视觉状态，不直接知道网易 Cookie 或响应结构 |

Catalog 围绕 Go 曲库服务的实际契约设计，不为了兼容网易或假想的多个平台建立统一大接口。推荐、评论、播客、云盘等在线能力不在首发范围，对应入口不出现在界面中。

### 5.1 媒体身份与能力

- 媒体在 Sonora 内有稳定身份；外部引用至少包含来源类型、实例/服务器、实体类型和原始字符串 ID。不要把所有外部 ID 强制转换成数字。
- 同名歌曲不自动视为同一首；多来源匹配另行设计，不能在播放失败后静默替换成别的录音。
- 队列中的一次出现有独立条目身份，允许同一首歌重复入队；删除、拖动和恢复按条目处理。
- `Track` 存元数据，`PlayableResource` 表达这次解析的临时播放资源、有效期和所需传输方式。过期地址不作为永久数据源保存。
- 喜爱、歌单编辑与播放历史由 Go 服务持久化；写入未确认时不能显示为已保存。
- 来源能力与当前权限分别判断。支持高音质不代表当前账号有权播放；失败返回明确原因，不映射成通用“网络错误”。

### 5.2 播放状态与异步规则

拟议状态：`idle → resolving → loading → playing / paused → ended`，失败进入 `error`；拖动、切歌和重试的事件由同一个 Playback Module 接收。

- 每次切歌分配请求标识并取消旧解析。用户先点 A 后点 B，即使 A 更晚返回，也不能覆盖 B。
- 暂停发生在解析中时，解析完成不得擅自自动播放；用户手势触发与浏览器自动播放限制要单独处理。
- 取地址失败、无权限、编码不支持、设备异常、用户取消分别表达；自动跳过要有上限，不能陷入无限循环。
- 歌词、封面、系统媒体信息和进度都跟随当前播放条目；旧事件不能修改新条目。
- 保存队列和播放位置，默认恢复为可继续播放的状态，不把启动后自动播放当成隐含承诺。

### 5.3 存储与凭据

结构化服务端数据由 Go 服务管理，数据库选型待定；浏览器只保存明确需要的本地设置、缓存和恢复状态。按实际需要选择 Web 存储方式，在阶段 2 验证迁移与恢复。

凭据只进入对应会话存储。SPlayer 参考实例的本机凭据由[浏览器会话说明](splayer-session.md)规定，每次无头访问都按该流程加载；凭据内容不写入文档、fixture、截图元数据、日志或 Git。Sonora 播放端不保存认证凭据，只持有服务端会话 Cookie；OIDC client secret 通过环境变量提供；管理员密码以慢哈希保存，不写入日志或配置示例；一次性初始化 token 仅在未初始化时写入容器日志，初始化后作废；远端请求参数和日志需要脱敏。参考实例的 Cookie 验证方式不作为 Sonora 的生产实现。

## 6. 样式还原与验收方法

本节是播放端交付的强制标准，按第 1 节的范围分两级：

- **播放器（严格复刻）**：全屏播放器、底部播放栏、播放队列抽屉的每个状态都要列出参考图，在相同环境、视口、主题、数据和交互状态下完成截图对照与交互检查，留下参考图、实际图、差异图和结论。布局、字号、间距、图标、颜色及动效的已知偏差未修正前，不能标记完成。
- **其他页面（视觉语言一致）**：只使用复刻自 SPlayer 的主题、样式与组件，不另起颜色、字号、圆角或阴影；新增的视觉元素经 Eric 确认。验收方式是检查组件与样式来源，并由 Eric 看过实际页面。主题、动态取色和设置项属于“视觉相关代码”，与原项目对照其生成结果（例如同一封面得到的 CSS 变量）。

两级都覆盖加载、空态、错误、悬停、焦点、选中、展开和窄窗口状态。首发范围决定哪些功能先交付，不能降低已交付部分的复刻精度。

无法消除的系统渲染差异须记录原因、复现条件和对比证据，由 Eric 明确确认例外；不得自行改设计、放宽全局阈值或替换基线使其通过。自研服务产生的新状态优先沿用原项目对应组件及视觉规范，涉及新增视觉方案时需明确确认。

### 6.1 基线采集

阶段 2 为播放器建立独立的“原项目参考图”和“Sonora 实际图”，不能用 Sonora 首次截图直接替代 SPlayer 基线。记录源码提交、系统、浏览器版本、字体、视口、DPR、主题、缩放、数据和交互步骤。

采集要覆盖：

| 区域 | 最低状态集合 |
| --- | --- |
| 底部播放栏 | 未播放、播放/暂停、进度拖动与悬浮信息、音量、错误 |
| 播放队列抽屉 | 空队列、有队列、当前曲目、悬停、拖动 |
| 全屏播放器 | 各播放器样式与背景样式、封面、普通/逐字歌词、翻译与音译、歌词定位、模式切换、元素自动隐藏 |
| 主题 | 明暗主题、主题色、封面取色得到的颜色 |

只验收桌面版 Chrome。先固定 `1440×1000` 作为桌面基线，再补充 `1280×800` 和 `1024px` 断点两侧的窄窗口；移动端布局与移动播放器不在范围内。断点以实际表达式为准，不能根据注释猜测。原 [useMobile.ts](../reference/SPlayer/src/composables/useMobile.ts) 同时含多组尺寸条件，需结合实际页面样式核对。

已有可从 [AppLayout.vue](../reference/SPlayer/src/layout/AppLayout.vue) 核对的起始尺寸：展开侧栏宽 `240px`、折叠宽 `64px`，显示底栏时侧栏高度扣除 `80px`；主内容横向内边距在移动与其他模式分别为 `16px` / `24px`。这些是样式盘点的起点，最终仍以具体状态的实际渲染为准，不用几个尺寸替代完整测量。

### 6.2 稳定且可信的比较

参考图直接截取本机参考实例，数据来自网易云；采集时同时记录歌曲数据，Sonora 用 fixture 复现同一组数据进行对照。需要重采时，参考图与数据快照整组更新。含账号个人信息的截图与快照只存放在 Git 已忽略的 `.local/` 下。固定字体和主题，等待字体与图片就绪；非动效截图暂停动画。首次协议弹窗单独覆盖，普通页面截图使用隔离的测试状态，不能为了截图修改用户实际协议记录。

使用 Playwright 截图比较和人工叠图检查。官方说明截图会受系统、浏览器和运行环境影响，因此同一套基线须在固定环境生成与验证。阈值先用重复采集的噪声校准；已确认固定区域以零差异为目标，对字体抗锯齿等噪声逐项记录例外，不通过放宽全局容差掩盖布局偏移。见 [Playwright 视觉比较](https://playwright.dev/docs/test-snapshots)。

动态背景和歌词动画另设时间点或可重复的时间轴检查；暂停动画后的静态图不能证明动效一致。基线更新必须说明原项目变化或已确认差异，不能把新实现的偏差直接“更新通过”。

## 7. 分阶段路线

阶段按退出条件推进，不给未经验证的日历工期。各阶段的工作包与当前状态见[阶段计划](phase/README.md)。Eric 决定先做管理后台，播放端随后进行。

1. **阶段 1：Go 服务基础与管理后台。** Go 服务骨架、管理员首次初始化与登录、曲库模型、上传入库、管理 API 与管理后台界面。
2. **阶段 2：播放端参照与页面清单。** 确定页面清单与设计取舍（2026-10-24 已确定），采集播放器参考图，验证 Chrome 音频能力。
3. **阶段 3：播放端视觉外壳。** 复刻主题与视觉相关代码，用固定数据实现主框架、首页、列表/详情、搜索和播放器展示层，建立播放器的视觉比较工具。
4. **阶段 4：播放端认证、API 与播放闭环。** 照搬 homepage 的 OIDC，播放端 API 与音频流，播放、队列、歌词与重启恢复。
5. **阶段 5：播放端功能页面。** 歌曲、专辑、艺术家、歌单、喜爱、历史、搜索和设置接入真实数据。
6. **阶段 6：首版。** 稳定性、性能、部署和视觉欠账清零。
7. **阶段 7：高级能力。** 候选池，逐项评估。

## 8. 验证与风险控制

| 风险 | 最早处理阶段 | 必须提供的证据 |
| --- | --- | --- |
| 外观相似但细节逐步漂移 | 2–3 | 原项目固定参考图、同数据对照、偏差记录 |
| 旧平台依赖残留 | 3–5 | 依赖约束及网络检查；Sonora 运行路径不含网易包、认证或请求 |
| 服务契约发生漂移 | 1、4 | 管理与播放端 API 的契约测试及版本兼容检查 |
| 异步切歌串状态 | 4 | 可控制响应先后顺序的测试；真实引擎切歌验证 |
| 上传入库与标签差异 | 1 | 多格式、缺标签、重复文件、损坏文件和大曲库的真实样本测试 |
| 管理员初始化被他人抢先 | 1 | 初始化须提供容器日志中的一次性 token；token 错误、过期与重复初始化的拒绝测试 |
| Chrome 音频兼容性或 Web 构建问题 | 2、4、6 | Chrome 音频样本、生产 Web 产物测试 |
| 数据和队列恢复错误 | 4、6 | 真实存储的重启、迁移、失败恢复测试 |
| 大列表、歌词和背景耗资源 | 3、6 | 固定数据规模的滚动/播放测量，持续运行记录 |
| 账号凭据泄漏 | 1、4 | 网络与日志脱敏检查、隔离的测试会话；Authelia 契约测试 |

单元测试重点放在状态机、队列、ID、DTO 转换、歌词时间和错误规则；存储使用真实数据库验证关键事务；端到端覆盖完整用户链路。视觉、真实音频和平台集成分别提供证据，不用某一类测试代替其他类别。

性能先建立基线：记录冷启动、搜索响应、首音延迟、大列表滚动、持续播放内存与 CPU。阶段 1–4 获得目标硬件上的实测后再设预算，不在没有测量时写“比原项目快”或虚构指标。

  cmd/sonora/           # 服务入口
  internal/admin/       # 初始化 token、管理员登录与会话
  internal/config/      # YAML 配置
  internal/devmode/     # 开发构建（-tags dev）的写死账号
