# 使用前端毫秒时间戳 LWW 与 PG 全局序列同步音乐文件，冲突按整条记录覆盖

Sonora 第一版由管理后台生产音乐文件，Tauri Android、macOS 终端消费并保存文件。本决策采用前端生成的毫秒级 `updatedAt` 做整条记录 LWW（Last Write Wins），以 PostgreSQL 全局 sequence 分配的 `serverVersion` 拉取增量。可写客户端先本地落库并标记待同步，每轮先上传再拉取；删除通过 `isDeleted` 传播，客户端收到删除直接执行，不比较时间戳。

当前为 `proposed`：规则供评审，尚未批准或实现，不维护核心测试用例。影响管理后台 Web client/server、终端本地数据库及文件同步流程。本文件是 `server/sync` 的根决策，没有前序 ADR；第一版建立新协议，不承诺兼容其他同步协议或迁移既有产品数据。播放列表同步留给后续决策。

## 问题与约束

管理后台负责音乐导入、修改与删除；服务端保存已接收的音乐记录和文件内容，向终端提供增量。终端需要在断网后继续使用已下载的文件，并在恢复连接后追上后台变化。后台的本地编辑也应先持久化，网络失败不能让修改只留在内存中。

不同设备可能离线修改同一条记录。第一版接受其中一个完整版本胜出，不维护编辑历史或合并不同字段；设备时钟决定胜负，服务端接收先后仅用于发现增量。音乐文件字节传输与记录同步有不同的失败边界，必须分别记录完成状态。

## D1：后台生产、终端消费，记录身份独立于文件路径

| 概念 | 本决策中的含义 |
| --- | --- |
| 生产者 | 管理后台；Web client 产生修改，server 校验、持久化并分发 |
| 消费者 | Tauri Android、macOS 终端；第一版拉取音乐记录并下载文件 |
| 音乐文件记录 | 具有稳定 `id` 的同步对象，描述音乐文件及其内容引用 |
| 文件内容 | 记录指向的音乐字节；与各设备的保存路径分离 |
| 待同步 | 本地修改尚未获得服务端明确处理结果的持久化状态 |
| 删除标记 | `isDeleted = true` 的记录，服务端保留以向离线客户端传播删除 |

`id` 在本地首次创建时生成，跨重试与设备保持稳定；重命名、移动和替换文件内容不改变记录身份。服务端在授权范围内按同一 `id` 判定冲突，客户端不得通过自报归属写入或拉取其他范围的数据。具体 ID 格式和账号模型另行设计。

第一版终端没有音乐目录写入职责，其上传阶段为空。终端下载、清理缓存或改变本地路径均不产生业务修改，不改写 `updatedAt`。可写客户端的同步规则先用于后台 Web client，不据此开放终端编辑或提前定义播放列表行为。

## D2：业务版本由 `updatedAt` 决定，等值保留接收方已有版本

`updatedAt` 是产生业务修改的前端所记录的 Unix epoch 毫秒整数，服务端不替换为接收时间。新记录可直接接收；已有记录仅在传入时间戳严格更大时被整条覆盖。比较与写入必须原子完成，不能让并发上传基于过期读取分别覆盖。

| 接收情形 | 处理 |
| --- | --- |
| 本地或服务端不存在该 `id` | 接收传入记录；删除按 D5 处理 |
| 传入 `updatedAt` 大于已有值 | 接收完整业务记录，覆盖原业务字段 |
| 传入 `updatedAt` 小于已有值 | 保留已有业务记录 |
| 传入 `updatedAt` 等于已有值 | 保留已有业务记录，即使内容不同 |
| 客户端收到 `isDeleted = true` | 直接删除，优先于以上时间比较 |

整条覆盖包括文件内容引用，不对标题、文件引用等字段分别合并。`serverVersion`、待同步状态、下载状态和本地路径属于同步或设备状态，不随业务记录整体复制；传入版本被忽略时，也可记录其处理结果或推进拉取游标。

例如 A、B 分别持有相同 `updatedAt`、不同标题的记录，交换后仍各自保留原值。协议不使用设备 ID 或 `serverVersion` 打破平局，因此不承诺所有副本最终内容一致。一次更新也可能覆盖另一设备对不同字段的修改，这是整条 LWW 的明确代价。

## D3：本地先落库，每轮先上传，再拉取

本地业务修改与待同步标记在同一事务持久化。上传发送持久化记录的快照；断网、超时和重启后仍能重试。同一客户端、同一同步范围只运行一轮同步，用户编辑可与网络请求并发。

服务端对每条上传返回明确结果：接收新版本、保留已有版本，或失败。保留已有版本是已处理的冲突结果，应返回服务端当前记录，使客户端即使已拉过其 `serverVersion` 也能按 D2/D5 处理；网络成功不能等同于记录写入成功。失败项继续待同步，已明确处理项可独立确认。一轮有限上传尝试结束后可以拉取，避免单个失败项长期阻塞消费。

上传确认在本地事务中重新核对 `updatedAt`，仅当当前记录仍是已发送的版本时清除待同步标记。为覆盖同毫秒内连续修改、时钟回拨及删除后重建，还必须核对持久化的本地修改代次；每次本地业务修改推进代次。代次只保护本地确认，不参与跨设备 LWW，也不打破时间戳平局。

例如上传快照时间为 `1000`，响应前用户改成 `1001`，旧响应不能清除新修改的待同步状态。同毫秒再次修改时，代次不同也不能清除。确认服务端已处理一个版本，只表示无需重传这个版本，不表示所有设备内容一致。

上传结果中的服务端当前记录按接收时的本地状态应用，不能无条件覆盖上传期间的新编辑。普通远端记录只有严格更新才覆盖本地并取代相应待同步修改；本地更新时保留待同步状态。删除例外见 D5。

## D4：`serverVersion` 使用 PG 全局 sequence，并保证提交可见顺序

所有进入本同步域的服务端有效记录变更，包括删除，使用同一个持久化 PG `bigint` sequence 分配 `serverVersion`。序列正向递增、不循环、`CACHE 1`；起始拉取游标为 `0`。只为实际接收的状态变化分配新版本；旧版本、等值上传和重复确认不制造业务变更。序列允许空洞，客户端不能等待缺失数字。跨 Web/Tauri 协议以十进制字符串无损传递版本，比较时按整数处理。

`serverVersion` 仅是增量发现顺序，不是冲突裁决依据。服务端写记录与记录版本在同一事务提交，响应只能报告已提交结果。

单独调用 `nextval()` 不足以安全推进游标：事务 A 取 `41` 尚未提交，事务 B 取 `42` 并提交，客户端拉到 `42` 后，晚提交的 `41` 将被永久跳过。这是基于 PG sequence 语义推导的失败场景；PG 明确规定取号不会因回滚而回收，并且大于一的缓存可能跨会话乱序。[Sequence 函数](https://www.postgresql.org/docs/current/functions-sequence.html)、[CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html)。

第一版所有同步写入必须先获取同一数据库事务级互斥锁，在锁内读取当前已提交状态、完成 LWW 判定、分配版本并写入，持锁到提交或回滚。禁止预先取号、绕过该入口写同步记录，或在锁内传输文件。事务级 advisory lock 可承载此规则，其生命周期由数据库事务管理。[PG 显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)。此处选择全局串行发布，换取简单且不会漏记录的游标；吞吐瓶颈留待有数据后评估。

拉取按固定授权范围查询已提交的 `serverVersion > cursor`，按版本升序分页，返回记录的当前完整状态（含删除标记），不承诺交付每个中间版本。客户端只能将游标推进至这一页实际处理到的最后版本；空页保留原游标。禁止用 sequence 当前值或上传响应版本直接推进拉取游标。

每页记录应用、文件任务持久化和游标推进必须在本地同一事务完成。被 D2 忽略的记录也算已处理；事务失败整页重试。下载无需在此事务中完成，但不能只推进游标而丢失文件任务。首次从 `0` 拉取现存记录与删除标记；当前授权范围变化时须重新建立对应同步范围，不能直接复用旧游标。

## D5：服务端保留删除标记，客户端收到后直接删除

生产者本地删除先落为 `isDeleted = true` 的待同步记录，收到服务端处理结果前不能直接丢失删除意图。上传删除在服务端仍按 D2 的时间戳规则接收：较旧或等值删除不会覆盖已有记录；删除被接收后获得新 `serverVersion`，以删除标记长期保留。第一版不清理服务端删除标记。

客户端收到服务端删除标记时，不比较本地 `updatedAt`，直接删除本地业务记录和对应待同步修改，并取消该记录的下载任务。即便本地编辑更新、尚未上传，也以收到的删除为准；服务端上传冲突结果携带的删除标记同样适用。重复接收删除应无害，后续旧上传响应不能重建已删除记录。

数据库删除与物理文件清理不是同一事务：客户端应持久化清理义务，重启后继续清理自己管理的副本；迟到下载在落地前复核记录和内容引用，不能让已删除文件重新出现。共享内容仍被其他记录引用时不能误删，用户的原始导入文件不属于终端缓存清理范围。

这不是永久禁止恢复：服务端仍可接收比删除标记时间更新的非删除记录。同一 ID 是否提供显式恢复操作留给后续产品决策；按当前 LWW 规则，更新的离线副本可能重新建立记录，不能宣称删除全局永久胜出。

## D6：音乐记录与文件内容分别同步，完整文件才算可用

音乐文件同步包含记录同步和文件传输两部分。记录携带稳定的内容引用及可校验的内容摘要、长度；发布新记录或替换内容前，生产者必须完成内容上传且服务端确认内容可用，之后才提交记录变更。内容引用指向不可变字节，替换字节产生新引用，不能原地改写旧引用代表的内容。

终端持久化记录后下载缺失内容，写入临时文件，完整性校验通过并完成本地发布后才标记可用。失败或断网保留可重试任务；不能把元数据已同步显示为文件已下载。记录在下载期间变化时，落地前核对当前内容引用；旧下载结果不能覆盖新目标。替换失败时不把旧文件标为新版本已完成。

此边界让文件传输失败与游标推进独立恢复。上传成功但记录未发布的孤立内容允许暂时存在，回收策略、对象存储选型、断点续传和本地路径布局由后续 ADR 决定；本根决策不规定 HTTP 路由或数据库表结构。

## 不变量

1. 同一记录的普通冲突仅由 `updatedAt` 的严格大小决定，相等保留接收方已有业务值。
2. 本地业务修改与待同步状态一起持久化，上传确认只清除所发送的本地修改代次。
3. 服务端有效变更与 `serverVersion` 原子提交，发布更高版本后不会再发布更低的新版本。
4. 拉取游标只覆盖已在本地持久化处理的增量，记录处理与文件任务不会因崩溃被游标跳过。
5. 客户端收到删除标记直接删除本地记录，服务端保留删除传播依据。
6. 文件只有在完整性校验通过且仍符合当前内容引用时，才能成为该记录的可用副本。
7. 第一版终端的本地文件管理不修改生产者的音乐记录。

## 为什么不是这些替代方案

| 替代方案 | 优势 | 本次取舍 |
| --- | --- | --- |
| 服务端接收时间 LWW | 不依赖设备时钟 | 离线旧操作晚到会胜出；本项目选择前端修改时间表达版本先后 |
| 字段级合并或 CRDT | 可保留更多并发编辑 | 需要逐字段定义合并语义及元数据；第一版明确接受整条覆盖的损失 |
| 相同时间戳按设备 ID 决胜 | 可提供确定性平局收敛 | 改变“相同时间戳保留各自已有值”的项目规则 |
| 按 `updatedAt` 拉取 | 少维护一个版本字段 | 回拨或落后设备的新上传可能小于游标而漏拉，必须独立记录服务端发布顺序 |
| 无发布互斥的 PG sequence | 写入并行度更高 | 取号与提交错序会漏拉，无法满足游标不漏记录的承诺 |
| 每轮全量复制 | 不需要增量游标 | 重复扫描和传输随音乐库规模增长；全量重建只用于重新建立同步状态 |
| 客户端保留墓碑并按时间比较删除 | 可保护较新的本地编辑 | 改变客户端收到删除直接执行的既定语义 |

## 风险与为什么不能直接改写

设备时钟领先可能压制其他设备很长时间，时钟回拨可能让新编辑输给旧版本；同毫秒不同内容可能永久分歧。本地修改代次只防误确认，不能修复这些业务冲突。当前接受这些限制，不把该协议描述为无损合并或无条件最终一致。

全局写锁限制发布吞吐，服务端删除标记长期占用存储。锁等待或事务失败应返回可重试失败，不能旁路锁继续发布。客户端删除可丢弃本地未上传编辑；恢复与内容回收需要额外生命周期规则。

投入使用后，不能直接重置 sequence、清空删除标记、改变时间单位或替换 ID，否则既有游标和身份会失效。需要此类改动时先记录后续 ADR，明确协议或同步范围的新版本；保全生产者待同步数据，再使受影响客户端重建快照和游标。备份恢复导致版本历史倒退时也必须使旧游标失效，不能把旧游标继续用于已回退的数据。

## 本决策未解决的问题

- 播放列表、顺序与成员关系的同步：涉及跨记录语义，不能直接推定整条覆盖已满足需求。
- 账号与音乐库授权模型、设备撤销：本决策仅要求范围隔离，具体身份与权限由对应领域决定。
- 文件传输协议、存储后端、容量策略和内容回收：需独立确定资源生命周期及跨平台落地方式。
- 时钟异常提示、冲突展示与显式恢复：当前记录其影响，后续决定用户如何观察和处理。
- 同步协议升级及快照重建协议：当前确立需要重建的边界，具体协商机制另行设计。

## 落地顺序

1. 评审根决策：确认生产消费边界、平局不收敛、删除例外和全局串行发布的代价。完成条件为规则纠偏后转为 `approved`，届时在镜像目录补充核心测试用例与验证义务。
2. 实现记录同步闭环：覆盖本地待同步、逐条上传结果、并发确认、PG 发布顺序、分页与删除。完成条件为对应核心义务有直接验证证据；从此阶段开始支持记录增量，尚不等于文件同步完成。
3. 接入文件传输与终端：实现内容先上传后发布、持久化下载与清理、校验及迟到任务防护。完成条件为 Android、macOS 在断网和重启后均能恢复并取得完整文件；D2 的冲突规则保持不变。
4. 按验证结果同步文档并转为 `implemented`：完成条件为记录和文件闭环均已验证，明确剩余边界，删除不再成立的实现推测。
